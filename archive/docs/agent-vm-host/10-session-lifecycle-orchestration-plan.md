# Session Lifecycle & Host Orchestration — Implementation Plan

## Blueprint

[[10-session-lifecycle-orchestration]] specifies the component that turns every other already-planned piece into a running, resourced, timed-out, and torn-down session — and the load-bearing architectural fact that there is no daemon anywhere in it: systemd owns process lifecycle end to end, and the CLI only ever renders session state and issues `systemctl` calls. Nothing in this component exists yet. The finished state this plan builds toward: a host-wide config file read fresh on every CLI invocation; a fully-wired per-session systemd unit graph (`agentvm-session@<id>.target` plus the VM unit and its four helper units) whose `BindsTo=`/`Requires=`/`After=`/`PartOf=` edges make launch atomic and every stop path converge on full teardown, by construction; a CLI (`launch`/`list`/`attach`/`detach`/`stop`/`review`/`transcript`, `doctor` stubbed) that is nothing but a thin renderer-and-caller around that graph; and a proven `max_concurrent_sessions` cap.

Build order follows the spec's own dependency chain: nothing downstream can read a knob until the config file exists, so configuration comes first; the unit graph is the actual object every other piece of this component manipulates, so it is built and proven (atomicity, stop cascades) before any CLI wraps it, one helper unit at a time so each addition is independently verifiable; the CLI then wraps the now-complete, already-provable graph — `launch` first since every other command only reads state `launch` produces; and the concurrency cap is proven last because it is an emergent property of `launch`'s cap-check plus the graph's own teardown behavior working together across multiple concurrent sessions, not something with independent content of its own.

This plan does not build:

- The real `jailer`/`firecracker` invocation (uid/gid from the slot, `Delegate=yes` cgroup mechanics, hugepage machine-config, `IPAddressDeny=any`) — [[12-production-hardening]] (no plan note yet). This plan's VM unit `ExecStart=` is an explicitly-flagged minimal/placeholder jailer invocation.
- The real content of `recv-bpf`, the stdio bridge (terminal tap + attach fan-out), and the idle timer's mtime-based watchdog check — [[11-session-transcript-receivers]] (no plan note yet). This plan owns those units' names, wiring, and cascade edges only; their `ExecStart=` scripts are explicitly-flagged placeholders that run and exit cleanly.
- [[13-error-handling-failure-modes]]'s described launch-atomicity and stop-cascade *behavior* — nothing separate is built for it. It falls directly out of this plan's unit graph (Chunk 2); 13's future plan should cite this plan's steps rather than re-deriving the mechanism.
- The VMM launch mechanics, guest pid1 boot sequence, mirror/git-service/device-image tools, and the mitmproxy engine/allowlist/credential-injection/slot-allocator internals — all already built by [[03-vmm-firecracker-plan]], [[04-guest-pid1-init-plan]], [[06-workspace-and-repo-delivery-plan]], and [[05-network-egress-control-plan]] respectively. This plan only invokes and wires those, with exact step anchors given at each point of use.

**Open gap check:** [[15-decisions-log]] has four items tagged against this spec. Three are settled and simply assumed throughout, not re-derived: "Host daemon / CLI process model — superseded" (no daemon anywhere in this design), "Host-side concurrency model — superseded" (struck; each per-session process is independently supervised by systemd, there is no shared event loop to describe), and "Host-wide config source" (a config file, resolved at Step 1.1). The fourth, "mitmproxy multi-listener support" (#open-question), lives at [[05-network-egress-control-plan#Step 5.2 — mitmproxy multi-listener wiring & slot-assignment file]] — this plan touches the slot mechanism at Steps 2.2 and 2.4 and notes there where the question lives, without re-resolving it.

This plan also flags two gaps of its own, found while grounding rather than guessed:

1. **No systemd unit for mitmproxy exists in any already-created plan.** [[05-network-egress-control-plan#Step 2.1 — mitmproxy TLS MITM core engine, CA, and singleton framing]] explicitly builds "the proxy engine program itself, directly runnable, not the unit file," and no later step in that plan revisits it — unlike [[06-workspace-and-repo-delivery-plan#Step 2.2 — Host-wide singleton systemd unit for the git service]], which did build its singleton's unit file. Since this plan's VM unit must `Requires=`+`After=` a real `agentvm-mitmproxy.service`, Step 2.2 below builds that missing unit, mirroring 06's Step 2.2 pattern, rather than leaving this plan's own graph unbuildable.
2. **Slot release on a non-CLI-triggered stop is not addressed by spec text.** §10 says `launch` acquires a slot and `stop` releases it, but says nothing about what releases a slot when a session ends via `RuntimeMaxSec=` or a helper-unit cascade instead of a CLI `stop`. Step 2.4 below resolves this with a systemd-native mechanism (`ExecStopPost=` on the VM unit, which runs on every stop regardless of trigger) rather than guessing at daemon-side bookkeeping the "no central daemon" decision already rules out.

## Chunks

1. **Chunk 1 — Host-wide configuration.** The config file schema, loader, and defaults every later chunk reads. (Step 1.1)
2. **Chunk 2 — Per-session systemd unit graph.** The target, the VM unit, all four helper units, the two singleton-service dependency edges (including patching the missing mitmproxy unit), and a full atomic-launch/stop-cascade proof. (Steps 2.1–2.6)
3. **Chunk 3 — The CLI.** `launch`, `list`/`review`/`transcript`, `attach`/`detach`, `stop`, and a stubbed `doctor` — thin wrappers around Chunk 2's graph. (Steps 3.1–3.4)
4. **Chunk 4 — Concurrency-cap proof.** `max_concurrent_sessions` enforcement proven under real concurrent launches. (Step 4.1)

## Step 1.1 — Config file schema, loader, and defaults

Chunk 1, single step. Foundation — no prior step exists yet in this plan.

```text
You are building a component of a Firecracker-based guest VM subsystem's host-side orchestration layer, from its specification, from scratch. Nothing has been implemented for this component yet.

Specification facts to ground this task in: there is no central daemon anywhere in this subsystem (resolved, see the decisions log) — the CLI steers systemd directly and reads its configuration fresh on every single invocation, since there is no long-lived process to read it once at startup. Host-wide knobs live in a config file, chosen over environment variables because more host-wide knobs are expected over time (default resource sizing, allowlist entries) and a file scales better than a pile of env vars. The specific knobs this file must carry today: `max_concurrent_sessions` (an integer sizing the host-wide concurrency cap), a default guest RAM size (250 MiB is the spec's chosen default, sized to fit a whole number of 2M hugetlbfs pages — 125 pages exactly, no leftover 4K fragment), a default guest vCPU count (an example value, e.g. 1-2, not per-task configurable in this version), and a default session wall-clock timeout (the value eventually fed to `RuntimeMaxSec=` on a session's VM unit). Do not add any knob not named here (e.g. no port numbers — those are fixed well-known constants owned by other already-built components, not reconfigured here).

Task: build a small config-loading library, in whatever language/tooling matches this repo's existing conventions for host-side orchestration code (this subsystem's orchestration language is Python), that: defines a schema for exactly the four knobs above with sensible built-in defaults for each (so a missing or partial config file still produces a fully-populated, usable configuration); loads and parses a config file at a stable, conventional path under `$XDG_CONFIG_HOME` (e.g. `$XDG_CONFIG_HOME/agentvm/config.toml`, falling back to the XDG default base directory if that variable is unset); merges file-provided values over the built-in defaults, so a config file only needs to override what it wants to change; validates that `max_concurrent_sessions` and the vCPU count are positive integers and the RAM size is a positive multiple of 2 MiB (matching the hugetlbfs-page-alignment reasoning above), raising a clear, specific error identifying which field failed validation if not. This library performs a fresh load on every call — it must not cache state across calls within a single process in any way that would defeat "read on each invocation" if reused inside a longer-lived test harness.

Verify: with no config file present, confirm the loader returns exactly the four built-in defaults. Write a config file overriding only `max_concurrent_sessions`, confirm the loader returns that override alongside the other three untouched defaults. Write a config file with an invalid value for each of the three validated fields in turn (a negative `max_concurrent_sessions`, a zero vCPU count, a RAM size not a multiple of 2 MiB) and confirm each produces a distinct, clearly-identified validation error rather than a silent fallback or a generic crash. This loader is what every later step in this component calls to learn the concurrency cap, default resource sizing, and default timeout — nothing downstream is built yet, but this proves the one artifact all of it will read.
```

## Step 2.1 — Session directory/metadata conventions and the target + VM-unit skeleton

Chunk 2, first step. Builds on Step 1.1's config loader for the VM unit's `RuntimeMaxSec=`/RAM/vCPU values. This is the first step that actually launches a session-shaped systemd unit, even though the four helper units it will eventually depend on don't exist yet.

```text
Context already built: a config loader exposing `max_concurrent_sessions`, default guest RAM (MiB), default vCPU count, and a default session timeout (seconds), read fresh on every call.

Specification facts to ground this task in: launching a session instantiates a templated set of systemd units, conceptually named `agentvm-session-<id>-*`, started together as one transaction via a wrapping target — `systemctl start` on that one target launches the whole session atomically. The VM unit execs jailer, which execs firecracker, chrooted, under a dedicated uid/gid per session (the real jailer flags belong to a different, not-yet-planned component — see the placeholder note below). `RuntimeMaxSec=<timeout>` on the VM unit enforces the session wall-clock cap declaratively, with no periodic reap process needed. There is no daemon-mutated JSON registry: `systemctl list-units`/`show` against the naming convention is the authoritative live-state source, and a thin per-session metadata file (repo, pinned commit, launch timestamp — written once at launch, never mutated) supplies only the fields systemd itself doesn't track.

A plan-level implementation decision for this task, not dictated verbatim by the spec's illustrative naming: build the per-session unit set as systemd *template* units (the `@` instance syntax), installed once as static unit files, rather than rendering full unit file text per launch. Every unit in this component's graph is therefore a family like `agentvm-session@.target`, `agentvm-session-vm@.service`, etc., and a real session's units are `agentvm-session@<id>.target`, `agentvm-session-vm@<id>.service` (systemd's own `%i` substitution, id after the `@`, not embedded mid-name as the spec's prose illustrates the concept) — the CLI (built in Chunk 3) only ever renders a session id and an `EnvironmentFile=`, never unit-file text. Because template units read per-instance parameters through `EnvironmentFile=/run/agentvm/sessions/%i/params.env` (a file this task's units reference but do not yet populate — Chunk 3's `launch` writes it before starting anything), for this task's own verification you must hand-write that one file for a single throwaway test instance id, standing in for what `launch` will do for real later.

Task: define and document the on-disk session-state convention this whole component uses from here on: a per-session directory at a stable path derived from the session id (e.g. `/var/lib/agentvm/sessions/<id>/`), holding a `metadata.json` (repo, pinned commit, launch timestamp — write-once) and a runtime parameters file consumed via `EnvironmentFile=` (slot index, device paths, session RAM/vCPU/timeout — populated by a real `launch` in a later chunk; for this task, a hand-written stand-in). Then build two systemd template unit files: `agentvm-session@.target` (a plain target with no `ExecStart=`, meant only to group and be started/stopped as one transaction) and `agentvm-session-vm@.service`, whose `ExecStart=` runs a minimal placeholder jailer/firecracker invocation (a short wrapper script that merely sleeps for a token duration and exits 0, explicitly flagged in your output as a stand-in for the real jailer/firecracker invocation — building that for real belongs to a different, not-yet-planned component), reading its RAM/vCPU/timeout values from the `EnvironmentFile=` above (falling back to Step 1.1's config defaults if a value is absent from that file), and declaring `RuntimeMaxSec=` from the resolved timeout value. Wire `agentvm-session-vm@.service` as a `PartOf=`+dependency of `agentvm-session@.target` (the target requires and orders after the VM unit) so starting the target starts the VM unit. Give the VM unit `Restart=no` (per the spec's blanket policy for every unit in this graph — a stopped unit is a decision, not a hiccup).

Verify: install both template units. Hand-write a single test instance's directory and `params.env` (a short session timeout, e.g. 5 seconds, to make the `RuntimeMaxSec=` check fast) and run `systemctl start agentvm-session@<test-id>.target`. Confirm the VM unit reaches active/running, then confirm systemd stops it on its own once the short `RuntimeMaxSec=` elapses, and confirm the target follows it down. Separately, start a second test instance with a normal-length timeout and run `systemctl stop agentvm-session@<test-id-2>.target` manually; confirm the VM unit stops immediately. This proves the skeleton — one real session-shaped unit, config-driven timeout, atomic start/stop via the target — before any helper unit exists.
```

## Step 2.2 — Host-wide singleton dependency wiring (git-service, and the missing mitmproxy unit)

Chunk 2, second step. Builds directly on Step 2.1's VM unit. Also patches the gap noted in the blueprint: no earlier plan produced a systemd unit for mitmproxy.

```text
Context already built: `agentvm-session@.target` and `agentvm-session-vm@.service` template units, the latter with a placeholder jailer/firecracker `ExecStart=`, config-driven `RuntimeMaxSec=`, and `Restart=no`, proven to start/stop atomically via the target and to self-terminate on its wall-clock timeout.

Specification facts to ground this task in: two services are host-wide singletons, started independently of any session and outliving all of them — `agentvm-git-service.service` and `agentvm-mitmproxy.service`. Every session's VM unit has a one-way `Requires=`+`After=` dependency on both (must be up before the session starts, but neither singleton's lifetime is coupled to any one session) — this is different in kind from the `BindsTo=` edges to the per-session helper units built in later steps.

`agentvm-git-service.service` already exists as a real, buildable systemd unit — see [[06-workspace-and-repo-delivery-plan#Step 2.2 — Host-wide singleton systemd unit for the git service]] — reference it by name only; do not rebuild it.

`agentvm-mitmproxy.service` does not yet exist anywhere as a systemd unit. [[05-network-egress-control-plan#Step 2.1 — mitmproxy TLS MITM core engine, CA, and singleton framing]] built the mitmproxy engine program itself as a directly-runnable long-lived process but explicitly deferred its unit file; [[05-network-egress-control-plan#Step 5.2 — mitmproxy multi-listener wiring & slot-assignment file]] extended that same engine to bind one TCP listen port per concurrency slot (base port plus slot index, sized by `max_concurrent_sessions`) via repeated `--mode regular@<port>` arguments, and built the slot-assignment file mechanism the engine's addon reads — again without a unit file. Whether mitmproxy's multi-listener support holds up is [[15-decisions-log|the mitmproxy multi-listener open question]], tracked at that same Step 5.2 — this task does not re-resolve it, only wires a unit around whatever that engine program already is.

Task: (a) add `Requires=agentvm-git-service.service` and `After=agentvm-git-service.service` to `agentvm-session-vm@.service` from the previous step. (b) Build the missing `agentvm-mitmproxy.service` systemd unit: a long-lived, restart-on-failure singleton service (mirroring the git-service unit's pattern — start automatically, keep running indefinitely, recover from a crash on its own, unlike this component's per-session `Restart=no` units, since this unit is not per-session and has no session-scoped state to lose), whose `ExecStart=` runs the mitmproxy engine program from the two 05-plan steps above, with a `--mode regular@<port>` argument repeated once per slot from `0` to `max_concurrent_sessions - 1` (read via Step 1.1's config loader) at a fixed, well-known base port. Do not add any `Requires=`/`After=`/`BindsTo=` edge pointing *at* this unit from within its own file — that direction belongs only to session-side units. (c) Add `Requires=agentvm-mitmproxy.service` and `After=agentvm-mitmproxy.service` to `agentvm-session-vm@.service` alongside the git-service edges from (a).

Verify: stop both singleton services if running, then attempt `systemctl start agentvm-session@<test-id>.target` (reusing Step 2.1's hand-written test instance) and confirm it fails to bring up the VM unit with both singletons down (or, if they auto-start via `Requires=`, confirm they are started first and the VM unit does not proceed until both report active). Start both singletons manually, confirm `agentvm-session-vm@.service` now starts cleanly. Stop the target (session) and confirm both singletons remain running, untouched — proving the one-way "must be up first, not coupled to any one session's lifetime" contract for both dependencies, not just the git-service one this plan didn't have to build itself.
```

## Step 2.3 — `recv-bpf` and stdio placeholder helper units

Chunk 2, third step. Builds on Steps 2.1–2.2's VM unit.

```text
Context already built: `agentvm-session-vm@.service`, config-driven `RuntimeMaxSec=`, `Requires=`+`After=` on both host-wide singletons (`agentvm-git-service.service`, `agentvm-mitmproxy.service`), `Restart=no`, wrapped by `agentvm-session@.target`.

Specification facts to ground this task in: the VM unit's per-session helper units are `BindsTo=`+`After=` targets of the VM unit — any one of them stopping (including a deliberate self-stop) stops the VM unit too, and they must be listening before the VM boots and starts talking to them. Two of those helper units are `agentvm-session-recv-bpf@.service` (the guest-initiated BPF transcript receiver, listening on this session's dedicated vsock UDS path for one guest-initiated connection with no handshake) and `agentvm-session-stdio@.service` (the host-initiated interactive stdio bridge: connects to the guest's interactive vsock port, fans out to `attach.sock`, tees to `terminal.jsonl`). Both units' *internal* behavior — the actual read loop, the 100 MB growth cap, the attach fan-out, the terminal tap — belongs to [[11-session-transcript-receivers]], which has no plan note yet; this task builds only these two units' definitions and their place in the dependency graph, standing in for that internal behavior with a placeholder. Both units have `Restart=no`, per this component's blanket policy (an auto-restarted receiver would undo its own future cap enforcement).

Task: build two systemd template units, `agentvm-session-recv-bpf@.service` and `agentvm-session-stdio@.service`, each with `Restart=no` and an `ExecStart=` that is an explicitly-flagged placeholder — a short script that touches (creates, zero-length) a file at a fixed, conventional path inside this session's directory (`bpf.jsonl` for the first, `terminal.jsonl` for the second — the same paths [[11-session-transcript-receivers]]'s real content will eventually write into), then sleeps indefinitely until signaled to stop, so each behaves like a real long-lived unit for dependency-graph purposes without doing any real receiving. State plainly in your output that these `ExecStart=` scripts are throwaway stand-ins, not [[11-session-transcript-receivers]]'s real deliverable. Add `BindsTo=agentvm-session-recv-bpf@%i.service agentvm-session-stdio@%i.service` and the matching `After=` to `agentvm-session-vm@.service`. On each of the two new units, add `PartOf=agentvm-session-vm@%i.service` (the reverse-direction edge: if the VM unit stops, these two stop too).

Verify: start the target for a test instance and confirm all three units (VM, recv-bpf, stdio) reach active, with the two helpers active before the VM unit per `After=`. Manually `systemctl stop` just `agentvm-session-recv-bpf@<test-id>.service` and confirm the VM unit and the stdio unit both stop as a result (the `BindsTo=` cascade). Start a fresh test instance and manually `systemctl stop` the VM unit directly; confirm both helper units stop too (the `PartOf=` cascade), and confirm the target follows. This proves bidirectional cascade for two of the eventual three helper units before the third (with its extra slot-allocation wiring) is added next.
```

## Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring

Chunk 2, fourth step. Builds on Step 2.3's two-helper graph, and on [[05-network-egress-control-plan]]'s already-built slot allocator and relay — unlike Step 2.3, this unit wraps real, already-built content, not a placeholder. This step also resolves the blueprint's second flagged gap (slot release on non-CLI stops).

```text
Context already built: `agentvm-session-vm@.service` with `BindsTo=`+`After=` on two placeholder helper units (`recv-bpf`, `stdio`), both `PartOf=` the VM unit, both proven to cascade in both directions; `Requires=`+`After=` on both host-wide singletons from Step 2.2.

Specification facts to ground this task in: the third helper unit, `agentvm-session-recv-proxy@.service`, is "the guest-initiated proxy-tunnel relay to mitmproxy" — explicitly *not* a transcript writer (that's mitmproxy's own addon writing `proxy.jsonl`, a host-wide singleton concern, not this unit's). Unlike `recv-bpf`/`stdio`, this unit's real content already exists: [[05-network-egress-control-plan#Step 2.2 — Host-side vsock↔TCP relay bridging guest shim to mitmproxy]] built the host-side vsock↔TCP relay program, and [[05-network-egress-control-plan#Step 5.3 — Slot-aware guest shim and host relay]] extended it to accept a slot index as a startup parameter and bridge to that slot's specific mitmproxy listen port. mitmproxy's per-session listen ports are drawn from the same fixed-size concurrency-slot pool [[05-network-egress-control-plan#Step 5.1 — Shared concurrency slot allocator]] built, sized by `max_concurrent_sessions` — "one shared slot allocator, not two independent pools," also backing jailer's future per-session uid/gid ([[12-production-hardening]], not built here). A session acquires a free slot at launch and releases it at stop; the slot-assignment file mapping a slot's port to this session's id/dir is kept current by that same acquire/release, per [[05-network-egress-control-plan#Step 5.2 — mitmproxy multi-listener wiring & slot-assignment file]] (also where the still-open mitmproxy multi-listener question is tracked, not re-resolved here).

A gap the spec leaves unaddressed, resolved here rather than guessed: nothing in §10 says what releases a session's slot when the session ends via `RuntimeMaxSec=` or a helper-unit crash cascade instead of a CLI `stop`. Resolution: add `ExecStopPost=` to `agentvm-session-vm@.service`, running a slot-release call against 05's allocator every time the VM unit stops, for *any* reason — this is a systemd-native guarantee, not daemon-side bookkeeping (which the "no central daemon" decision rules out). This is a secondary backstop; the primary release path (a `launch` that fails before the VM unit ever starts) is Chunk 3's job, not this unit's.

Task: build the systemd template unit `agentvm-session-recv-proxy@.service`, `Restart=no`, whose `ExecStart=` runs the real slot-aware relay binary from [[05-network-egress-control-plan#Step 5.3 — Slot-aware guest shim and host relay]], reading this session's dedicated vsock UDS path and its assigned slot index from the `EnvironmentFile=` established in Step 2.1 (hand-write a test value for this task's own verification, standing in for `launch`'s future real write). Add `BindsTo=`+`After=` for this unit to `agentvm-session-vm@.service` alongside the two from Step 2.3, and add `PartOf=agentvm-session-vm@%i.service` on this new unit, completing all three helper units in both directions. Add `ExecStartPre=` on `agentvm-session-vm@.service` that calls 05's allocator to acquire a slot for this session id and records the result into this session's `EnvironmentFile=` (or confirms an already-recorded slot matches an existing allocation, for restart-of-the-same-instance-id safety), and `ExecStopPost=` on the same unit that releases that slot back to the allocator, clearing its slot-assignment-file entry, regardless of why the unit stopped.

Verify: with a real slot pool (small, e.g. size 2, via Step 1.1's config), start a test instance's target and confirm all three helper units and the VM unit reach active, the relay is reachable on the assigned slot's mitmproxy port (per 05's own slot-pool verification pattern), and the slot-assignment file shows this session's id against that port. Stop the target manually and confirm the slot-assignment file entry clears. Start a second test instance, this time let it die via a short `RuntimeMaxSec=` instead of a manual stop, and confirm the slot is *still* released (proving `ExecStopPost=` fires regardless of stop trigger) — this is the concrete proof the blueprint's second flagged gap is actually resolved, not just described. Finally, manually stop just `agentvm-session-recv-proxy@<test-id>.service` and confirm the VM unit and the other two helpers all cascade down, exactly as Step 2.3 proved for the other two units.
```

## Step 2.5 — Idle-timer watchdog wiring

Chunk 2, fifth step. Builds on Step 2.4's complete three-helper-unit graph.

```text
Context already built: `agentvm-session-vm@.service` with `BindsTo=`+`After=` on all three real/placeholder helper units (`recv-proxy` real, `recv-bpf`/`stdio` placeholder), each `PartOf=` the VM unit, slot acquire/release wired via `ExecStartPre=`/`ExecStopPost=`, all proven to cascade bidirectionally.

Specification facts to ground this task in: a fourth unit pair, `agentvm-session-idle@.timer` + `agentvm-session-idle@.service`, is the inactivity watchdog — independent of and in addition to the VM unit's own `RuntimeMaxSec=` wall-clock cap. Unlike the three helper units above, this pair is `PartOf=` the VM unit only, one-way (torn down with the session, but stopping it does *not* itself cascade back up to stop the VM unit — it is not a `BindsTo=` target of the VM unit). The timer fires roughly every 60 seconds; the real check — read the three transcript files' mtimes, and if the combined silence exceeds 600 seconds, stop one of the three helper/bridge units (letting the already-proven `BindsTo=` cascade from Steps 2.3–2.4 do the rest) — is [[11-session-transcript-receivers]]'s content, not yet planned. This task builds only the timer's schedule and the service's place in the dependency graph, with the check itself an explicitly-flagged placeholder.

Task: build `agentvm-session-idle@.timer` (a systemd timer unit firing `agentvm-session-idle@.service` on a recurring ~60-second interval, started/stopped alongside the target) and `agentvm-session-idle@.service`, whose `ExecStart=` is an explicitly-flagged placeholder script that only logs a timestamped "watchdog tick" line and exits cleanly — it must not actually stop anything yet, since the real mtime-based decision logic belongs to [[11-session-transcript-receivers]]. Add `PartOf=agentvm-session-vm@%i.service` to both the timer and the service (the one-way, VM-stops-therefore-this-stops edge). Do not add any `BindsTo=`/`Requires=` edge from the VM unit pointing at either of these — the VM unit's own dependency list from Steps 2.3–2.4 is unchanged by this step.

Verify: start a test instance's target and confirm the idle timer and its service are both active alongside the other four units. Manually `systemctl stop agentvm-session-idle@<test-id>.service` (simulating the placeholder tick failing or being stopped) and confirm the VM unit and the other three helper units are *unaffected* — proving the one-way direction (unlike Steps 2.3–2.4's helpers, this unit stopping must never cascade upward). Then manually stop the VM unit directly and confirm the idle timer and service both stop too, alongside the other three helpers — proving the downward `PartOf=` cascade reaches this fourth pair exactly like the other three.
```

## Step 2.6 — Full unit-graph atomic-launch and stop-cascade proof

Chunk 2, sixth and final step. Builds on every unit from Steps 2.1–2.5 — this is the capstone that closes the chunk by proving the whole graph at once, and is the concrete mechanism [[13-error-handling-failure-modes]]'s future plan should cite instead of re-deriving.

```text
Context already built: the complete per-session systemd unit graph — `agentvm-session@.target` wrapping `agentvm-session-vm@.service` (config-driven `RuntimeMaxSec=`, `Requires=`+`After=` on both host-wide singletons, `ExecStartPre=`/`ExecStopPost=` slot acquire/release, `Restart=no`), `BindsTo=`+`After=` on three helper units (`recv-proxy` real, `recv-bpf`/`stdio` placeholder, each `PartOf=` the VM unit, each `Restart=no`), and `agentvm-session-idle@.timer`+`.service` (`PartOf=` the VM unit only, one-way).

Specification facts to ground this task: launching a session's full unit graph is meant to be one atomic systemd transaction — a failure in any required unit (jailer failing its chroot setup, a helper failing to bind its vsock path) fails the whole `systemctl start agentvm-session@<id>.target` transaction, with no orphaned half-started session and no manual cleanup path. Three independent triggers (manual stop, `RuntimeMaxSec=` wall-clock timeout, a helper stopping on its own for any reason) must all converge on the same full-teardown outcome via the `BindsTo=`/`PartOf=` structure already built — this is exactly the behavior [[13-error-handling-failure-modes]] describes as launch atomicity and stop cascades, and this task's job is to prove that behavior is real, not to add anything new for it.

Task: write a small integration-test harness (matching this repo's existing testing conventions) that exercises the complete graph from Steps 2.1–2.5 together, with no code changes to any unit — this step is proof, not new construction. The harness must cover: (a) a normal launch where every unit starts cleanly, confirming all six units (target, VM, three helpers, idle timer+service counted as one pair) reach active as one transaction; (b) an induced failure in one helper unit's placeholder `ExecStart=` (make it exit non-zero instead of sleeping, for this test only) before the VM unit starts, confirming the whole target transaction fails and no unit is left running — no orphaned half-started session; (c) each of the three `BindsTo=` helper units stopped individually after a clean launch, confirming the VM unit and the remaining helpers all cascade down every time, not just for the one helper exercised in Steps 2.3–2.4 individually; (d) a short `RuntimeMaxSec=` timeout expiring, confirming the same full cascade (including the idle timer pair) as a manual stop produces; (e) a manual `stop` on the target, confirming identical cascade behavior to (c) and (d) — proving all three triggers converge on the same mechanism, as the spec requires.

Verify: run the harness and confirm all five scenarios pass with the exact unit-state outcomes described above, and confirm scenario (b) leaves the session directory's slot allocation untouched (nothing was acquired, since `ExecStartPre=` for that failed launch either never ran or its own failure is itself covered by the transaction rollback — confirm which, and confirm no slot leak either way). This closes Chunk 2: [[10-session-lifecycle-orchestration]]'s entire per-session unit graph is now built and its atomicity/cascade properties are machine-checked, ready for Chunk 3's CLI to do nothing more than call into it.
```

## Step 3.1 — `launch`

Chunk 3, first step. Builds on Chunk 2's complete, proven unit graph and Step 1.1's config loader — this is where session directories, `EnvironmentFile=`s, and device images actually get created for real, replacing every hand-written stand-in used in Chunk 2's own verification.

```text
Context already built: a config loader (Step 1.1) and a fully-wired, atomicity-and-cascade-proven per-session systemd unit graph (Chunk 2) — `agentvm-session@.target`, its VM unit, three `BindsTo=` helper units, and an idle-timer pair — that so far has only ever been exercised against hand-written test session directories and `EnvironmentFile=`s.

Specification facts to ground this task in: `launch` renders the unit set for a new session id and runs `systemctl start agentvm-session@<id>.target`, returning as soon as that call returns — it does not block for the session's duration. `max_concurrent_sessions` is enforced by `launch` counting currently-active session units before starting a new one, rejecting the launch with no units created and nothing started if already at the cap. The host fetches/updates its local mirror on-demand, immediately before each task launch (not on a timer), and every session starts from fresh upstream state — see [[06-workspace-and-repo-delivery-plan#Step 1.1 — Host-local git mirror creation & on-demand fetch tool]]. Device 2 (the pinned-commit workspace checkout) and device 3 (the empty per-task writable overlay) are built per launch via [[06-workspace-and-repo-delivery-plan#Step 3.1 — Device 2: shallow-clone workspace-checkout image]] and [[06-workspace-and-repo-delivery-plan#Step 3.2 — Device 3: empty writable overlay image]] respectively — this task calls both tools fresh on every launch; neither plan built any commit-level image-reuse/caching, so none is invented here either. A session's launch-time metadata (repo, pinned commit, launch timestamp) is written once and never mutated.

Task: build the `launch` CLI subcommand: (1) load config via Step 1.1; (2) count currently-active `agentvm-session@*.target` units (the naming convention Step 2.1 settled on) and reject immediately — printing a clear "at capacity" message, creating no session directory, acquiring no slot, starting no unit — if the count is already at `max_concurrent_sessions`; (3) generate a new opaque session id; (4) invoke [[06-workspace-and-repo-delivery-plan#Step 1.1 — Host-local git mirror creation & on-demand fetch tool]] for the requested repository, then resolve the commit to pin (the mirror's current default branch tip, unless a specific commit/ref was requested); (5) invoke the device-2 and device-3 build tools cited above to produce this session's two workspace images; (6) create the session directory (per Step 2.1's convention), write `metadata.json` (repo, pinned commit, launch timestamp) and the `EnvironmentFile=` (device paths, RAM/vCPU/timeout resolved from config unless a future per-launch override is added — none is in this version); (7) run `systemctl start agentvm-session@<id>.target`; (8) return immediately without waiting for the session to finish. On failure of step (7), surface the failing unit's `systemctl status`/journal output to the user, and explicitly release any slot this launch's own `ExecStartPre=` may have acquired before the transaction failed (the secondary release path noted in Step 2.4 — check whether systemd's transaction rollback already ran `ExecStopPost=` for a unit that started-then-failed, and only release here for the case where the VM unit never started at all).

Verify: with `max_concurrent_sessions` set low (e.g. 1) and no sessions running, launch one session and confirm it reaches active with a real device-2/device-3 image pair built from a real (throwaway test) mirror and commit, a populated `metadata.json`, and the mirror actually fetched (confirm via the mirror tool's own idempotency proof — a second launch against the same repo picks up a new commit if one was added upstream in between). With that one session still running, attempt a second `launch` and confirm it is rejected before anything is created — no new session directory, no slot acquired, nothing started. Stop the first session and confirm a subsequent `launch` now succeeds.
```
