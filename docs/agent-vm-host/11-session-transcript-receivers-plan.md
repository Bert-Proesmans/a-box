# Session Transcript & Stream Receivers — Implementation Plan

## Blueprint

[[11-session-transcript-receivers]] specifies three per-session `.jsonl` transcript files — `terminal.jsonl`, `proxy.jsonl`, `bpf.jsonl` — plus an inactivity watchdog that stops a session after 10 minutes of combined silence across all three. This is not a re-executable recording; it exists for human review/audit, queryable directly via DuckDB/SQLite. Two of the three files are dumb byte tees with a hard 100 MB cap (`bpf.jsonl` via a dedicated `recv-bpf` receiver, `terminal.jsonl` via the stdio-bridge's own tap); the third (`proxy.jsonl`) is written by mitmproxy's own addon and deliberately uncapped.

Unusually for this wave, almost none of this plan's raw mechanism is unbuilt: [[07-bpf-monitoring-plan]]'s Chunk 4 already built and end-to-end-proved the exact growth-bounded receiver `bpf.jsonl` needs, and [[10-session-lifecycle-orchestration-plan]]'s Chunk 2 already built the full systemd unit graph — target, VM unit, all three `BindsTo=` helper units, and the idle-timer pair — with explicitly-flagged placeholder `ExecStart=` scripts standing in for exactly this plan's content, and already machine-proved launch atomicity and stop-cascade behavior generically (Step 2.6). This plan's job is narrower than a from-scratch build in three of its four chunks: wire already-proven pieces into 10's real unit graph, build the one genuinely new piece (the terminal-transcript tap's reader-thread/fan-out design and the `proxy.jsonl` addon), and prove each capped stream's cap-hit concretely triggers the real cascade rather than relying on 10's generic proof alone.

Build order: `recv-bpf` first (Chunk 1) since it is pure wiring of already-built, already-proven code — lowest risk, fastest to close. Terminal-transcript tap second (Chunk 2) since it is the one substantial new build (`session_manager.py`), sequenced core-reader-thread → attach fan-out → real-graph integration so each step produces something independently working. `proxy.jsonl` third (Chunk 3): fully independent of Chunks 1–2, depends only on already-built pieces of [[05-network-egress-control-plan]] and [[10-session-lifecycle-orchestration-plan]]. Inactivity watchdog last (Chunk 4) because it structurally depends on all three transcript files existing and being touched-at-startup, which only holds once Chunks 1–3 are wired for real.

This plan does not build: the VMM/vsock device model or per-VM dedicated UDS path scheme ([[03-vmm-firecracker]], already planned), the guest pid1-init boot sequence ([[04-guest-pid1-init]], already planned), the BPF program/loader or its capture logic and NDJSON schema, or the `bpf.jsonl` receiver's own read-loop/cap internals ([[07-bpf-monitoring]] / [[07-bpf-monitoring-plan]], already built — Chunk 1 below only wires it in), the mitmproxy engine, allowlist, credential-injection addon, or slot allocator/assignment-file mechanism ([[05-network-egress-control]] / [[05-network-egress-control-plan]], already built — Chunk 3 below only consumes it), the systemd unit graph's names, dependency edges, or atomic-launch/stop-cascade *mechanism* itself ([[10-session-lifecycle-orchestration]] / [[10-session-lifecycle-orchestration-plan]], already built — this plan only supplies real `ExecStart=` content for its flagged placeholders), the stop-cascade's own semantics ([[13-error-handling-failure-modes]], no plan yet — this plan only triggers it), and any shared DuckDB/SQLite query tooling (the spec states the schema is queryable that way as a property of the format, not something to build).

**Open gap check.** Five [[15-decisions-log]] items are directly relevant and already resolved, folded into the steps below rather than re-derived: "Transcript stream delivery & growth bounding — revised" (100 MB cap on `terminal.jsonl`/`bpf.jsonl` only, `proxy.jsonl` deliberately uncapped — the split this whole plan follows); "Inactivity watchdog" (10-minute combined-silence threshold via mtimes + a per-session timer, reusing the existing stop cascade — Chunk 4); "`proxy.jsonl` per-session split" (owned by [[05-network-egress-control-plan#Step 5.2 — mitmproxy multi-listener wiring & slot-assignment file]], consumed at Step 3.1); "`proxy.jsonl` content: resolved IP + credential-injection audit" (owned by [[05-network-egress-control-plan#Step 4.1 — Credential injection addon]], consumed at Step 3.1); "Terminal-transcript wire-level mechanism" (the `session_manager.py` single-reader-thread/fan-out design Chunk 2 implements). [[05-network-egress-control-plan]]'s still-open "mitmproxy multi-listener support" question is a load-bearing assumption for Chunk 3 but is not re-resolved here — it lives at that plan's Step 5.2.

This plan also flags two gaps found while grounding, neither guessed at nor silently patched into another plan:

1. **Per-line schema asymmetry.** The spec states all three files share "a common schema (timestamp, session ID, stream/event type, payload)." `proxy.jsonl`'s addon already resolves `session_id` per flow (it must, to pick which file to append to) and can trivially embed it per line. `bpf.jsonl` and `terminal.jsonl`, by contrast, are dumb byte tees — [[07-bpf-monitoring-plan#Step 2.2 — DNS-attempt capture and the common export schema|07's plan explicitly decided]] the guest-side exporter must *not* embed a session identifier, and the host-side receiver does no parsing/rewriting of what it appends. Session identity for those two files is structural (one file per session directory), not per-line. Whether the spec's "common schema" line means literally per-line for all three, or per-line-where-natural plus path-derived elsewhere (e.g. via DuckDB's `read_json_auto(..., filename=true)`), is not stated. Flagged, not resolved by adding a rewriting layer to either already-built dumb receiver.
2. **File-touch-at-startup ordering for `bpf.jsonl`.** The idle watchdog's correctness depends on every stream's file existing at zero length *before* any real byte can arrive, so pre-connection silence doesn't misread as already-idle. This plan's own Step 2.1 makes `session_manager.py` do this explicitly for `terminal.jsonl`. Whether [[07-bpf-monitoring-plan#Step 4.1 — Standalone, growth-bounded receiver|07's already-built receiver script]] opens its output file immediately at process start (before accepting the guest connection) or only on first write is not stated in that plan. Flagged at Step 4.2 as a cross-plan integration question for 07's plan to confirm or amend — not fixed here.

## Chunks

1. **Chunk 1 — `recv-bpf` real wiring & cap-cascade proof.** Wires [[07-bpf-monitoring-plan]]'s already-built, already-proven growth-bounded receiver into [[10-session-lifecycle-orchestration-plan]]'s real unit graph, replacing its Step 2.3 placeholder, and proves the cap-hit concretely triggers the real stop cascade. (Step 1.1)
2. **Chunk 2 — Terminal-transcript tap (`session_manager.py`).** The shared background reader thread, tee-to-`terminal.jsonl`, attach-client fan-out, and the same 100 MB cap discipline — replacing 10's Step 2.3 and Step 3.3 placeholders with the real stdio bridge. (Steps 2.1–2.3)
3. **Chunk 3 — `proxy.jsonl` transcript addon.** The mitmproxy addon [[05-network-egress-control-plan]] anticipated but deliberately left unbuilt: session resolution via the slot-assignment file, uncapped append, wired into 10's already-real mitmproxy singleton unit. (Step 3.1)
4. **Chunk 4 — Inactivity watchdog.** Pure, fake-clock-testable mtime-comparison logic, then real wiring into 10's idle-timer placeholder, triggering the same stop cascade Chunks 1–2 already proved. (Steps 4.1–4.2)

## Step 1.1 — `recv-bpf`: real receiver wiring & cap-cascade proof

Chunk 1, single step. Replaces the placeholder `ExecStart=` in [[10-session-lifecycle-orchestration-plan#Step 2.3 — `recv-bpf` and stdio placeholder helper units]] with the receiver [[07-bpf-monitoring-plan#Step 4.1 — Standalone, growth-bounded receiver]] already built and [[07-bpf-monitoring-plan#Step 4.2 — End-to-end proof against real guest output]] already proved against a real guest — this step does not rebuild that script.

```text
Context already built, not to be rebuilt here: a standalone, growth-bounded receiver script (07-bpf-monitoring-plan's Step 4.1) that accepts one guest-initiated connection on a dedicated socket path, runs a dumb read/append/sleep loop with no parsing of event contents, and enforces a hard 100 MB cap — once hit, it stops reading, closes the accepted connection, closes/unlinks the listening socket, and exits, with no line-boundary trimming and no drain-and-discard. That script was already proved standalone against synthetic bytes and, separately, end to end against a real guest's BPF export connection via an ad hoc launcher (07's Step 4.2) — not through the real per-session systemd unit graph. Separately, a systemd template unit `agentvm-session-recv-bpf@.service` already exists (10-session-lifecycle-orchestration-plan's Step 2.3), currently pointed at a throwaway placeholder ExecStart= (touches bpf.jsonl, sleeps indefinitely), with Restart=no already set and BindsTo=/After=/PartOf= edges to the VM unit already wired and proven to cascade in both directions (10's Steps 2.3 and 2.6). A per-session directory/EnvironmentFile= convention (session directory path, dedicated per-VM vsock UDS path) already exists from 10's Step 2.1.

Specification facts grounding this task: recv-bpf is authenticated structurally, not by any CID lookup — Firecracker's vsock device gives each VM a dedicated uds_path, so a guest-initiated connection on the BPF-export port surfaces at a path unique to this one session; there is no cross-session ambiguity to resolve. Restart=no is deliberate: an auto-restarted receiver would silently reopen the very socket its own cap enforcement just closed, defeating the mechanism — this rationale is already reflected in 10's unit, not something to re-add here.

Task: replace agentvm-session-recv-bpf@.service's placeholder ExecStart= with an invocation of 07-bpf-monitoring-plan's Step 4.1 receiver script, passing it (via the EnvironmentFile= convention 10's Step 2.1 already established) this session's dedicated BPF-export vsock UDS path and an output file path of <session_dir>/bpf.jsonl. Make no changes to the receiver script's own internals (read-loop, cap logic, exit behavior) — this task is integration wiring only. Do not attempt to resolve the file-touch-at-startup open gap noted in this plan's blueprint; if the script does not already create bpf.jsonl at zero length before accepting a connection, note that observation in your output rather than patching 07's script.

Verify: launch a real session through 10's real launch/stop CLI (not a standalone harness) with this real ExecStart= wired in. Drive guest activity that produces BPF events and confirm bpf.jsonl fills in the session directory in near real time. Separately, drive enough guest-side activity to cross the 100 MB cap and confirm: the recv-bpf unit exits per its own already-proven cap logic, and 10's already-proven BindsTo= cascade (Step 2.6) tears down the VM unit and the other two helpers as a concrete result of this specific trigger — closing the loop on error-handling-failure-modes' third stop-cascade trigger (a receiver hitting its cap) with a real, not synthetic, example.
```

## Step 2.1 — Terminal tap core: reader thread, tee, and growth cap

Chunk 2, first step. Builds `session_manager.py`'s core against [[10-session-lifecycle-orchestration-plan#Step 2.3 — `recv-bpf` and stdio placeholder helper units|10's Step 2.3]] placeholder stdio-bridge unit (explicitly flagged there as this component's real content to supply), reusing Chunk 1's cap discipline as the pattern to mirror.

```text
Context already built: 10-session-lifecycle-orchestration-plan's per-session directory/EnvironmentFile= convention (Step 2.1); a placeholder agentvm-session-stdio@.service unit (Step 2.3) that currently only touches terminal.jsonl and sleeps, explicitly flagged there as a stand-in for this component's real content; a placeholder attach.sock echo extension (10's Step 3.3), also flagged as a stand-in. Chunk 1's Step 1.1 proved a dumb read/cap/close-on-cap loop for bpf.jsonl — this task mirrors that same cap discipline for terminal.jsonl.

Resolved in the decisions log ("Terminal-transcript wire-level mechanism"), settled design to implement here: the interactive stdio channel and the terminal-transcript tap are literally the same host-initiated vsock connection, observed from the host side as one persistent connection. session_manager.py holds this connection with a single background reader thread owning the only recv() calls on it, logging every chunk to terminal.jsonl and broadcasting it to whichever attach clients are currently connected; attach clients themselves (built in the next step) are handled by separate per-client threads that only ever call sendall() on the shared connection, so there is no reader contention.

Specification facts for this task: recording happens regardless of attach state — detaching a client must never touch the underlying guest connection. The same 100 MB hard-cap policy recv-bpf uses applies here too: once cumulative bytes written to terminal.jsonl reaches the cap, stop reading, close the connection, and exit — no line-boundary trimming, no drain-and-discard. Each receiver/tap must create/touch its output file immediately at startup, before any real byte arrives, so the future idle watchdog never misreads pre-connection silence as already-idle.

Task: build session_manager.py's core. On startup, before performing any read: create terminal.jsonl in this session's directory at zero length. Establish the host-initiated vsock connection to the guest's interactive port via Firecracker's CONNECT <port>\n handshake against this session's dedicated per-VM UDS path (the transport scheme already established elsewhere in this project's vsock work — perform the handshake and hold the resulting connection here; do not redesign the transport). Run one background reader thread that owns the only recv() calls on this connection: read a bounded chunk, append it verbatim to terminal.jsonl, then call a broadcast function with that same chunk against an in-memory list of registered attach-client output callbacks — for this step, leave that list permanently empty and unpopulated (attach-client registration is the next step's job; build the call site now so the next step only has to populate the list, not restructure this thread). Track cumulative bytes written to terminal.jsonl; once the 100 MB cap is reached, stop reading, close the connection, and exit. This unit already has Restart=no set at the systemd level (10's Step 2.3) — add no restart logic of your own.

Verify: point this script at a real guest's dedicated stdio vsock port directly (via the existing VMM launcher, not yet through 10's full unit graph — that integration is a later step). Confirm terminal.jsonl exists at zero length before any guest output arrives. Confirm guest output is appended verbatim as it streams. Confirm pushing output past the 100 MB cap stops the reader, closes the connection, and exits, mirroring recv-bpf's already-proven cap behavior from Chunk 1.
```

## Step 2.2 — Attach-socket fan-out to N clients

Chunk 2, second step. Builds on Step 2.1's reader thread and empty broadcast list; replaces [[10-session-lifecycle-orchestration-plan#Step 3.3 — `attach`/`detach`|10's Step 3.3]] placeholder echo extension with real fan-out.

```text
Context already built: session_manager.py's core (Step 2.1) — a background reader thread that owns the only recv() on the session's stdio vsock connection, tees every chunk to terminal.jsonl, enforces the 100 MB cap, and calls an empty broadcast function per chunk. Separately, 10-session-lifecycle-orchestration-plan's Step 3.3 bound attach.sock and, as an explicitly-flagged stand-in, echoed whatever a client sent back to that same client — proving the CLI's attach/detach raw-passthrough path works, but not real fan-out.

Specification facts for this task: multiple attach clients may be connected simultaneously; the reader thread is the only thing that ever reads from the guest connection, so every attach client's input must reach the guest by writing directly onto the shared connection, never by the client's own thread reading from it. Detaching one client must never affect another already-attached client or the underlying guest connection.

Task: extend session_manager.py to bind attach.sock at the fixed path 10's Step 2.1 convention reserves. Accept multiple simultaneous client connections; spawn one thread per connected client that: (a) on connect, registers a callback into Step 2.1's broadcast list so the reader thread's tee immediately begins delivering output to this client; (b) reads whatever the client sends and calls sendall() with it directly on the shared guest connection (never recv()s from that connection itself); (c) on disconnect, deregisters its callback from the broadcast list and closes only its own client socket, leaving the guest connection and every other attached client untouched. Confirm multiple simultaneously attached clients each independently receive every broadcast chunk — true fan-out to N, not delivery to only one.

Verify: run this script against a real guest connection as in Step 2.1. Attach two simultaneous raw test clients to attach.sock; send input from one and confirm it reaches the guest (via an observable guest-side effect); confirm both clients receive the same broadcast output. Disconnect one client and confirm the other keeps receiving output uninterrupted and the guest connection itself is unaffected.
```

This closes out error-handling-failure-modes' third stop-cascade trigger for both of this plan's capped receivers.

## Step 3.1 — `proxy.jsonl` transcript addon

Chunk 3, single step, fully independent of Chunks 1–2. Builds the addon [[05-network-egress-control-plan#Step 5.2 — mitmproxy multi-listener wiring & slot-assignment file|05's plan anticipated but explicitly deferred]], wiring it into [[10-session-lifecycle-orchestration-plan#Step 2.2 — Host-wide singleton dependency wiring (git-service, and the missing mitmproxy unit)|10's already-real `agentvm-mitmproxy.service` unit]].

```text
Context already built, not to be rebuilt here: a mitmproxy engine enforcing an allowlist and injecting the real Anthropic credential (05-network-egress-control-plan's Steps 2.1, 3.1–3.2, 4.1), the last of which tags each flow's metadata with a credential_injected boolean and exposes the destination IP mitmproxy actually connected to via its own connection object. Separately, that same engine binds one TCP listen port per concurrency slot and maintains an on-disk slot-assignment file mapping each slot's listen port to the current occupant's session_id/session_dir, kept current by a shared allocator's acquire/release calls (05's Steps 5.1–5.2) — that plan explicitly built the file format and update mechanism "without building the addon itself" that would consume it. Separately, agentvm-mitmproxy.service already exists as a real (non-placeholder) systemd unit (10-session-lifecycle-orchestration-plan's Step 2.2), its ExecStart= already running the multi-listener engine with the allowlist and credential-injection addons loaded.

Specification facts for this task: proxy.jsonl records, per request/response, the destination host/port as requested, the resolved IP mitmproxy actually connected to, and the credential_injected flag — deliberately not redacted like the header value itself, since knowing when the secret went out is the point. Unlike bpf.jsonl/terminal.jsonl, proxy.jsonl is deliberately uncapped: capping it risks truncating exactly the audit trail it exists to preserve, so no byte limit or cap-triggered close applies here.

Task: build a mitmproxy addon module that, for every flow once it completes: reads the local port the connection arrived on (flow.client_conn.sockname) and looks it up against the slot-assignment file to resolve the current session_id/session_dir; if no current mapping exists for that port (e.g. a race at slot release), drop the event for that flow rather than guessing a session — this is a narrow, accepted edge case, not something to add retry/backoff logic for. For a resolved flow, construct one NDJSON line carrying at minimum a timestamp, the resolved session_id, a stream/event-type discriminator, the destination host/port as requested, the resolved destination IP, and the credential_injected boolean — then append that line to <session_dir>/proxy.jsonl, with no cap of any kind. Wire this addon into agentvm-mitmproxy.service's already-real ExecStart= alongside the existing allowlist/credential-injection addons — an addition to that unit's addon-loading arguments, not a new unit or a rebuild of the existing ones.

Verify: using 05's own per-slot verification pattern (two acquired slots, two concurrent guest-shaped clients), send an allowed request through each slot's mitmproxy port and confirm each produces a correctly-tagged proxy.jsonl line in its own session's directory only — never cross-appearing in the other session's file — with resolved IP and credential_injected values matching 05's Step 4.1 behavior (true for the Anthropic destination, false for the git-loopback destination). Separately, push one session's proxy traffic volume well past 100 MB and confirm proxy.jsonl keeps growing uncapped and no connection is closed by this addon, in explicit contrast to Chunks 1–2's capped receivers.
```

## Step 4.1 — Idle-watchdog mtime-comparison logic

Chunk 4, first step. Independent of Chunks 1–3's code; only needs the three-file-per-session-directory convention from [[10-session-lifecycle-orchestration-plan#Step 2.1 — Session directory/metadata conventions and the target + VM-unit skeleton]].

```text
Context already built: 10-session-lifecycle-orchestration-plan's per-session directory convention, under which terminal.jsonl, bpf.jsonl, and proxy.jsonl all live.

Specification facts for this task: a session is stopped after 10 minutes of combined silence across all three transcript streams — total silence across all three, not a per-channel independent timeout. The mechanism needs no new IPC: each file's own mtime is the last-activity signal, for free, since each receiver/tap only writes its file when real bytes arrive and touches it at startup before any real byte. The check itself: take max(mtime) across the three files; if now - max(mtime) exceeds a threshold (600 seconds in the real system), the session is idle.

Task: build a small, pure, unit-testable function or module: given the three file paths (any of which may not yet exist — treat a missing file as maximally stale, not as an error), an injectable clock (a callable returning "now", not a direct system-time call, so a test can supply a fake clock), an injectable mtime-lookup (a callable given a path returns its mtime, not a direct filesystem stat call, so a test can supply fake files with no real filesystem I/O), and a threshold parameter defaulting to 600 seconds, compute max(mtime) across the three paths via the injected lookup and return whether now - max(mtime) exceeds the threshold. This function performs no I/O of its own — only the injected dependencies touch a clock or a filesystem.

Verify: exercise this function directly with fake clocks and fake mtimes, no real files and no real sleeping involved. Confirm it reports not-idle when all three mtimes are recent relative to the fake clock; confirm it reports idle once the max mtime is older than the threshold; confirm a missing file is treated as maximally stale without raising an error. This is exactly the needs_kvm-free unit-test scenario 14-testing-strategy names for the idle watchdog.
```

## Step 4.2 — Idle-watchdog real wiring & stop-cascade trigger

Chunk 4, second and final step, closing the plan. Builds on Step 4.1's pure logic and replaces [[10-session-lifecycle-orchestration-plan#Step 2.5 — Idle-timer watchdog wiring|10's Step 2.5]] placeholder, reusing the cascade [[10-session-lifecycle-orchestration-plan#Step 2.6 — Full unit-graph atomic-launch and stop-cascade proof|10's Step 2.6]] already proved and Chunks 1–2 already triggered concretely for their own caps.

```text
Context already built: Step 4.1's pure, injectable mtime-comparison function. Separately, 10-session-lifecycle-orchestration-plan's Step 2.5 already wired agentvm-session-idle@.timer (firing agentvm-session-idle@.service on a ~60-second recurring interval) and agentvm-session-idle@.service (currently a placeholder that only logs a "watchdog tick" and exits, explicitly flagged there as this component's real content to supply), both PartOf= the VM unit only (one-way: this service stopping never cascades upward, but the VM unit stopping tears these down too). 10's Step 2.6 already proved that any one of the three BindsTo= helper units stopping cascades to tear down the whole session, regardless of which one.

Task: replace agentvm-session-idle@.service's placeholder ExecStart= with a real check script: read this session's directory path from the same EnvironmentFile= convention used throughout this plan, call Step 4.1's pure function against the three real file paths (terminal.jsonl, bpf.jsonl, proxy.jsonl) using the real clock and a real stat-based mtime lookup as its injected dependencies, and — only when the function reports idle — run systemctl stop against exactly one of the three BindsTo= helper units for this session (an arbitrary but fixed choice, e.g. the stdio-bridge unit; which one doesn't matter, since 10's Step 2.6 already proved any one stopping cascades identically). Add no new stop-cascade logic — this task only decides when to make the one systemctl stop call the graph already knows how to propagate. Leave the timer's ~60-second recurrence interval unchanged from 10's Step 2.5. Accept the idle threshold as an overridable parameter (default 600 seconds) so this task's own verification can use a short threshold instead of waiting the real 10 minutes, mirroring the short-timeout-for-testing pattern 10's own plan already used for RuntimeMaxSec=.

Open gap, flagged rather than resolved here: whether 07-bpf-monitoring-plan's already-built recv-bpf receiver script creates bpf.jsonl at zero length before accepting its guest connection (the same guarantee Step 2.1 explicitly built into session_manager.py for terminal.jsonl) is not stated in that plan. If it does not, a session could read as falsely idle or falsely active in the narrow window before the guest's first BPF event arrives. Note this as an integration question for 07's plan to confirm or amend — do not patch 07's script from within this task.

Verify: launch a real session via 10's CLI, generate activity on all three streams, and confirm the watchdog does not stop it. Then let a second session go fully silent on all three streams and, using a short overridden threshold, confirm the watchdog fires at approximately that threshold (not before) and the full cascade (10's Step 2.6 mechanism) tears down the entire session — matching 14-testing-strategy's needs_kvm "Idle watchdog" scenario: an idle session is stopped at the threshold, an active one is left alone. This closes the plan: all three transcript streams and the inactivity watchdog supervising them are now fully implemented and provable against the real per-session unit graph 10-session-lifecycle-orchestration-plan built.
```
