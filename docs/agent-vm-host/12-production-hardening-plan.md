# Production Hardening & Resource Control — Implementation Plan

## Blueprint

[[12-production-hardening]] specifies the layer that turns an already-launchable session (built by [[10-session-lifecycle-orchestration-plan]]) into a production-hardened one: real hugepage-backed guest memory instead of a config-less default, a real jailer invocation in place of a placeholder sleep script, host kernel tuning for a multi-tenant KVM host, and a `doctor` command that actually reports host health instead of a no-op stub. Nothing in this plan's scope exists yet — every target it touches currently holds an explicitly-flagged placeholder built by [[10-session-lifecycle-orchestration-plan]] specifically so this plan could replace it.

Build order follows the spec's own layering: the hugetlbfs pool must exist and be verified at host boot before any machine-config PUT can request `2M` pages from it, and `nx_huge_pages=never` must land alongside that pool per the spec's explicit "decide together, not as an independent checkbox" framing, so Chunk 1 closes out hugepages completely before anything else depends on it. Chunk 2 (jailer + systemd) depends on Chunk 1 only loosely (the hugepage machine-config field and the jailer argv are independent concerns that happen to share a unit file) and depends directly on the shared concurrency-slot allocator [[05-network-egress-control-plan]] already built — the jailer argv is split into a pure, unit-testable function (Step 2.1) before it is wired into the real unit (Step 2.2), mirroring the "pure function, unit-tested without root/KVM" pattern [[14-testing-strategy]] names for this exact case. Chunk 3 (KVM/host tuning) is host-wide config independent of any single session and the most novel/uncertain part of the spec (the `kvm-pit` placement risks), so it's sequenced after the session-shaped work is solid. Chunk 4 (`doctor`) comes last because it reports on everything the first three chunks produce — hugepage pool state, cgroup version, jailer/unit health — so it has nothing to report until they exist.

Finished state: a host that boots with a correctly-sized, verified hugetlbfs pool and `nx_huge_pages=never`; a VMM launcher whose machine-config PUT actually requests `2M` pages; a real jailer invocation (unique per-session uid/gid from the shared slot allocator, explicit `--cgroup-version 2`, no `--daemonize`) wired into `agentvm-session-vm@.service` with `Delegate=yes` and `IPAddressDeny=any` added as unit directives; `min_timer_period_us` and `nosmt` set explicitly in host config; a working `kvm-pit` cgroup-placement `ExecStartPost=` script with its two open risks turned into integration tests rather than assumptions; and a `doctor` subcommand reporting real hardware-mitigation, hugepage, cgroup, and unit-health status.

This plan explicitly does **not** build: the cgroup v2 mount itself or its boot-time verification guard (already built by [[02-host-platform-plan#Step 3.1 — Mount cgroup v2 as the only hierarchy]] / [[02-host-platform-plan#Step 3.2 — cgroup v2-only verification guard]] — this plan only targets that mount, never remounts or re-verifies it); the host memory swap/KSM posture guard (already built by [[02-host-platform-plan#Step 4.1 — Swap-disabled, KSM-disabled memory posture guard]], whose own text already names this plan's `doctor` command as its future reporting surface — folded into Step 4.1 below, not rebuilt); the shared concurrency-slot allocator itself (already built by [[05-network-egress-control-plan#Step 5.1 — Shared concurrency slot allocator]] — this plan only calls its existing acquire/release/lookup surface for uid/gid derivation, never a second pool); the per-session systemd unit graph, its atomicity/cascade proofs, the config loader, or any CLI command other than `doctor` (all already built by [[10-session-lifecycle-orchestration-plan]] — this plan only replaces two of its explicitly-flagged placeholders, described step by step below); any live-proxied-traffic rate limiter (the spec finds no Firecracker API mechanism for it — [[03-vmm-firecracker|the Vsock device schema has no rate-limiter field]] — and defers it to host software in [[05-network-egress-control]] if ever wanted; not built here or there); and any resolution of the still-open resource-limits-to-unit-property mapping question (see the open gap check below).

**Open gap check:** the spec's grounding brief for this plan named two decisions-log items as still open against [[12-production-hardening]]. Re-reading the current [[15-decisions-log]] directly (not the paraphrase), only one of those two is actually still open there: **"Resource limits → systemd unit property mapping"** (#open-question — which of the spec'd cgroup knobs, `blkio.throttle.*`/`memory.limit_in_bytes`/`cpu.shares`/`cfs_quota_us`/jailer's own `fsize`/`no-file`, become declarative unit directives like `MemoryMax=`/`CPUQuota=`/`IOWeight=` versus jailer's own raw `--cgroup`/`--resource-limit` flags). This plan flags it explicitly at Step 2.2 rather than guessing at a mapping the spec never commits to. The second item named in the brief, "Host memory: swap and KSM," is **not** in the decisions log's "Still open" section as of this reading — it appears under resolved decisions, already implemented by [[02-host-platform-plan#Step 4.1 — Swap-disabled, KSM-disabled memory posture guard]] (which explicitly names this plan's `doctor` command as its own future reporting surface). This plan treats it as resolved and out of scope to build, surfacing only its status through Step 4.1 below — see the report back to the task's caller for this discrepancy.

## Chunks

1. **Chunk 1 — Hugepages & `nx_huge_pages`.** Static hugetlbfs pool sizing at host boot, the paired `nx_huge_pages=never` kernel module parameter, and the `huge_pages` machine-config field wiring. (Steps 1.1–1.3)
2. **Chunk 2 — Jailer + systemd process isolation.** The real jailer invocation argv as a pure, unit-tested function, then its wiring into the real VM unit with `Delegate=yes`, `--cgroup-version 2`, and `IPAddressDeny=any`. (Steps 2.1–2.2)
3. **Chunk 3 — KVM/host tuning.** `min_timer_period_us` and `nosmt` host kernel tuning, then the `kvm-pit` cgroup-placement `ExecStartPost=` script. (Steps 3.1–3.2)
4. **Chunk 4 — The `doctor` subcommand.** Hardware-mitigation/hugepage/cgroup-version reporting, then jailer/systemd unit-health reporting, replacing the stub. (Steps 4.1–4.2)

## Step 1.1 — Hugepages: static pool sizing at host boot

Chunk 1, first step. Foundation for this plan — nothing in this plan precedes it. Reads the concurrency-cap and default-RAM knobs [[10-session-lifecycle-orchestration-plan#Step 1.1 — Config file schema, loader, and defaults]] already established, without rebuilding that loader.

```text
You are building a component of a Firecracker-based guest VM subsystem's host-side hardening layer, from its specification, from scratch. Nothing in this plan has been implemented yet.

Specification facts to ground this task in: guest memory is backed by pre-allocated hugetlbfs pages in `2M` mode, chosen despite snapshotting being out of scope for this project (the usual reason to prefer `2M` doesn't apply here, but the choice is made anyway). Default guest RAM per session is 250 MiB — exactly 125 hugetlbfs 2M pages, no leftover 4K fragment. The hugetlbfs pool is statically sized at host boot via NixOS's own kernel/sysctl configuration (`boot.kernel.sysctl."vm.nr_hugepages"` or equivalent) — not allocated or resized dynamically per VM launch. Pool size is `250 MiB × max_concurrent_sessions`. Both numbers already exist as knobs in the host-wide config loader built at [[10-session-lifecycle-orchestration-plan#Step 1.1 — Config file schema, loader, and defaults]] (`max_concurrent_sessions`, default guest RAM) — that loader reads a runtime TOML file fresh on every CLI invocation, while this task's NixOS sysctl setting is evaluated once at host build/boot time. These are two genuinely independent config systems with no shared source at build time in this design: an undersized pool causes erratic guest behavior/SIGBUS in a guest rather than a clean failure, so this is a real, spec-acknowledged operational risk, not a bug this task is expected to eliminate — document it explicitly rather than papering over it.

Task: add NixOS host configuration setting `boot.kernel.sysctl."vm.nr_hugepages"` (or the equivalent hugetlbfs pool-size mechanism) to a fixed value equal to `(250 MiB / 2 MiB) × max_concurrent_sessions` 2M-pages, with the `max_concurrent_sessions` value entered directly in this Nix configuration (there is no way to read the CLI's runtime TOML config from Nix-eval time in this design). Add a prominent comment directly above the setting stating plainly that this number must be kept in sync by hand with the CLI config's own `max_concurrent_sessions` value, and that a mismatch causes SIGBUS-class guest failures rather than a clean rejection — this is the standing operational risk the specification itself calls out, not something this task resolves. Add a boot-time verification check, following the same pre-flight-diagnostic pattern already established in [[02-host-platform-plan#Step 2.2 — Boot-time KVM availability verification]] and [[02-host-platform-plan#Step 3.2 — cgroup v2-only verification guard]], that confirms the configured hugetlbfs pool size actually matches what the kernel reports as available (`HugePages_Total` in `/proc/meminfo`), failing loudly rather than silently if the two disagree (a real signal that the pool didn't allocate as configured, distinct from the config-vs-CLI manual-sync risk above).

Verify: boot the host and confirm the check reports the pool healthy with `HugePages_Total` matching the computed value. As a negative-path proof, temporarily configure a mismatched pool size in a test configuration and confirm the check now fails loudly with a clear message, rather than passing silently. This is the first piece of functionality this plan produces: a real, host-boot-verified hugetlbfs pool, ready for `nx_huge_pages` to be decided alongside it (next step) and for a real VM to request pages from it (Step 1.3).
```

## Step 1.2 — `nx_huge_pages=never` module parameter

Chunk 1, second step. Builds on Step 1.1's pool. The spec is explicit this must be decided alongside the hugepage choice, not treated as an independent checkbox — this step extends, not duplicates, Step 1.1's verification check.

```text
Context already built: a NixOS host configuration with a statically-sized hugetlbfs pool (`vm.nr_hugepages`, sized to `250 MiB × max_concurrent_sessions` in 2M pages, with the manual-sync risk against the CLI's runtime config documented in-place) and a boot-time verification check confirming the kernel reports that same pool size.

Specification facts to ground this task in: KVM's default iTLB-multihit mitigation (`nx_huge_pages`) splits its own guest-physical→host-physical (EPT/NPT) mappings for executable regions down to 4K, independent of whether the underlying host memory is hugetlbfs-backed. Left at its default, this silently negates the entire point of choosing `2M` hugepages for executable guest memory — the spec treats this as a decision that must be made alongside the hugepage choice from the previous step, not an independent checkbox. The chosen mitigation is `nx_huge_pages=never`, a KVM kernel module parameter, applied via the same mechanism this plan's later host kernel tuning uses (`boot.extraModprobeConfig` or equivalent, i.e. `options kvm nx_huge_pages=never`), made explicit in host config rather than an ad hoc one-off `modprobe` call. This is chosen over cgroup v2's `favordynmods` remount alternative, which the spec also mentions but doesn't select.

Task: add `options kvm nx_huge_pages=never` (or the NixOS-idiomatic equivalent) to the host's `boot.extraModprobeConfig`, with a comment directly tying it to the hugepage pool from the previous step so a future reader doesn't treat the two as unrelated settings. Extend the previous step's boot-time verification check in place (do not create a second, separate check) to also confirm `/sys/module/kvm/parameters/nx_huge_pages` reports `never` at runtime, failing loudly alongside — but distinguishably from — the existing hugepage-pool-size check if it doesn't.

Verify: boot the host and confirm the extended check reports both the hugepage pool size and `nx_huge_pages=never` healthy together. As a negative-path proof, temporarily omit the modprobe config in a test configuration and confirm the check now fails specifically on the `nx_huge_pages` condition, with the hugepage-pool-size condition still reported separately and correctly — the two failure modes must be distinguishable, not collapsed into one generic error. This closes the host-side half of Chunk 1; Step 1.3 makes the pool actually reachable by a real Firecracker launch.
```

## Step 1.3 — Firecracker machine-config `huge_pages` wiring

Chunk 1, third and final step. Extends the machine-config PUT call [[03-vmm-firecracker-plan#Step 2 — Minimal boot proof: one root disk, captured boot log]] already issues. Also closes out the hugepage boot-time benchmark named in [[14-testing-strategy]].

```text
Context already built: a host with a statically-sized, boot-verified hugetlbfs pool (`vm.nr_hugepages`) and `nx_huge_pages=never` set and verified together.

Specification facts to ground this task in: the `2M` hugepage mode is wired into Firecracker's own `FirecrackerVM`'s `/machine-config` PUT request via a `huge_pages` field, set alongside `vcpu_count`/`mem_size_mib` — these are fields on the same API call, not separate requests. [[03-vmm-firecracker-plan#Step 2 — Minimal boot proof: one root disk, captured boot log]] built the VMM launcher that configures and starts a Firecracker microVM instance — that step's launcher necessarily already issues this initial machine-config PUT, since Firecracker requires `vcpu_count`/`mem_size_mib` to accept it and boot at all, even though that step's own text doesn't name the API call or these fields explicitly. This task extends that exact call, not a new one.

Task: extend the VMM launcher from [[03-vmm-firecracker-plan#Step 2 — Minimal boot proof: one root disk, captured boot log]] (as further extended by that plan's Steps 3–6) so its machine-config PUT call includes a `huge_pages` field set to request `2M` pre-allocated hugetlbfs-backed guest memory, alongside the existing `vcpu_count`/`mem_size_mib` fields, sourced from the same default guest RAM/vCPU knobs established at [[10-session-lifecycle-orchestration-plan#Step 1.1 — Config file schema, loader, and defaults]]. Add a launcher-level guard that the requested `mem_size_mib` is a value the previous two steps' hugetlbfs pool can plausibly satisfy for one more session (checked against the pool's known total configured size, not just trusting the caller blindly) — refusing the launch with a clear error rather than letting Firecracker fail with a guest-visible SIGBUS if the pool looks exhausted by this host's own accounting.

Verify: launch a microVM instance through the extended launcher with `huge_pages` set to `2M` and confirm, via the guest's own `/proc/meminfo` or an equivalent in-guest check using the placeholder init program from [[03-vmm-firecracker-plan#Step 2 — Minimal boot proof: one root disk, captured boot log]], that guest memory is actually hugetlbfs-backed, not just requested. As the `needs_kvm` hugepage boot-time benchmark named in [[14-testing-strategy]], launch the same guest configuration twice — once with `huge_pages` set to `2M` and once left at `None` — and record and compare boot time between the two, proving the measurement mechanism itself works end to end (the spec does not mandate a specific expected delta; this proves the benchmark is repeatable, not that a particular number is achieved). This closes Chunk 1: the hugepage pool is sized, verified, mitigated against `nx_huge_pages`, and now actually reachable by a real Firecracker launch.
```

## Step 2.1 — Jailer invocation argv (pure function, unit-tested)

Chunk 2, first step. Consumes the shared concurrency-slot allocator from [[05-network-egress-control-plan#Step 5.1 — Shared concurrency slot allocator]] for uid/gid derivation — one shared allocator, not a second pool. Produces a pure function only; wiring it into the real unit is Step 2.2.

```text
Context already built: a per-session concurrency-slot allocator ([[05-network-egress-control-plan#Step 5.1 — Shared concurrency slot allocator]]) that hands out and releases integer slot indices from a fixed-size pool sized by `max_concurrent_sessions`, with persisted state safe for concurrent, separately-invoked callers — already consumed by [[10-session-lifecycle-orchestration-plan#Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring]]'s `ExecStartPre=`/`ExecStopPost=` on `agentvm-session-vm@.service`, which records the acquired slot index into that session's `EnvironmentFile=` before the VM unit's `ExecStart=` ever runs.

Specification facts to ground this task in: every session's `firecracker` process runs under `jailer` (bundled in the same nixpkgs `firecracker` derivation — verified: `1.16.1` ships `firecracker` + `jailer` + others in one `bin/`, no extra packaging needed). Jailer alone provides: chroot via `pivot_root` into `<chroot_base>/<exec_file_name>/<id>/root`; always a new mount namespace; a `setuid`/`setgid` drop to a unique uid/gid per concurrent session. That uid/gid pair is derived from the *same* per-session concurrency slot [[05-network-egress-control-plan#Step 5.1 — Shared concurrency slot allocator]] already built for mitmproxy's per-session listen ports — one shared slot allocator backing both resources, not two independent pools; do not build a second allocator here, only a deterministic derivation (e.g. a fixed uid/gid base plus the slot index) from the slot index this session already has recorded in its `EnvironmentFile=`. Jailer's own default is `--cgroup-version 1`; this host mounts cgroup v2 only ([[02-host-platform|the host's cgroup v2-only mount]]), so `--cgroup-version 2` must be passed explicitly — an unspecified value would target a hierarchy that doesn't exist on this host. Jailer is invoked without `--daemonize`: with `--daemonize` but no `--new-pid-ns`, jailer's PID and firecracker's PID differ, so killing jailer alone would not kill firecracker — running jailer in the foreground, directly as the unit's `ExecStart=` (systemd tracks the real jailer/firecracker process tree in its own cgroup), avoids that orphan risk without needing `--new-pid-ns`.

Task: build a pure, side-effect-free function — following this repo's existing pattern of small, independently unit-testable "build a plan" functions for privilege-related setup (the `14-testing-strategy` note names this exact pattern, mirroring the existing capability-drop-plan style already used elsewhere in this codebase) — that takes typed inputs (session id, chroot base directory, path to the `firecracker` binary, the guest kernel/disk-image paths, the per-VM dedicated vsock UDS path, and the slot index recorded by [[10-session-lifecycle-orchestration-plan#Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring]]'s `EnvironmentFile=`) and returns the complete jailer argv list: `--id`, `--exec-file`, `--chroot-base-dir`, `--uid`/`--gid` (derived from the slot index via a fixed base offset, documented inline), `--cgroup-version 2`, and no `--daemonize`. The function performs no I/O of its own — no process spawning, no filesystem writes — only argv construction, so it can be tested without root or KVM.

Verify: write unit tests (no VM, no root needed, per [[14-testing-strategy#Jailer invocation argv]]) covering: a normal case producing the expected full argv for a given slot index; two different slot indices producing two distinct, non-overlapping uid/gid pairs; confirmation that `--cgroup-version 2` and no `--daemonize` are always present regardless of inputs; and a rejected/erroring case for an out-of-range slot index (one beyond the pool size the allocator would ever hand out). This produces the argv-construction logic Step 2.2 wires into the real VM unit — nothing in this step spawns a process yet.
```

## Step 2.2 — Wire jailer argv into the VM unit: `Delegate=yes`, `--cgroup-version 2`, `IPAddressDeny=any`

Chunk 2, second and final step. Replaces the placeholder `ExecStart=` from [[10-session-lifecycle-orchestration-plan#Step 2.1 — Session directory/metadata conventions and the target + VM-unit skeleton]] with a real invocation built from Step 2.1's argv function, and adds the two unit-level directives that plan's own text explicitly deferred to this one.

```text
Context already built: a pure jailer-argv-construction function (Step 2.1) taking a session id, chroot base, binary/image paths, vsock UDS path, and slot index, returning a full jailer argv with `--uid`/`--gid` derived from the slot, `--cgroup-version 2`, and no `--daemonize`. Also already built: `agentvm-session-vm@.service` ([[10-session-lifecycle-orchestration-plan#Step 2.1 — Session directory/metadata conventions and the target + VM-unit skeleton]]), whose `ExecStart=` is currently an explicitly-flagged placeholder ("a short wrapper script that merely sleeps for a token duration and exits 0") standing in for exactly this task's real content, and whose `ExecStartPre=`/`ExecStopPost=` ([[10-session-lifecycle-orchestration-plan#Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring]]) already acquire/release this session's slot index and record it into the unit's `EnvironmentFile=` before/after this `ExecStart=` runs.

Specification facts to ground this task in: `Delegate=yes` on the VM unit lets systemd own the top of the cgroup v2 subtree while jailer creates its own nested cgroup underneath for the VM's threads, without the two fighting over the same cgroup node (cgroup v2's "no internal process constraint"). `IPAddressDeny=any` (no `IPAddressAllow=` needed) on the VM unit is a defense-in-depth backstop, since the VM process has no legitimate network need at all — only a local vsock UDS — alongside the [[05-network-egress-control|egress allowlist]]'s own enforcement. Killing the unit/scope must reliably kill the whole cgroup (the orphan risk jailer's own docs call out) — this is exactly what `Delegate=yes` plus jailer running without `--daemonize` (Step 2.1) achieves together, with no `--new-pid-ns` needed.

One item is a still-open, unresolved decision, not to be guessed at here: [[15-decisions-log|"Resource limits → systemd unit property mapping"]] (#open-question) — whether cgroup knobs (`blkio.throttle.*`, `memory.limit_in_bytes`, `cpu.shares`/`cfs_quota_us`, jailer's own `fsize`/`no-file`) become declarative unit directives (`MemoryMax=`, `CPUQuota=`, `IOWeight=`) or jailer's own raw `--cgroup`/`--resource-limit` flags is undecided. Do not add any resource-limit directive or flag of either kind in this task — only `Delegate=yes` and `IPAddressDeny=any`, which are settled, are added here.

Task: replace `agentvm-session-vm@.service`'s placeholder `ExecStart=` with a real one that: reads this session's slot index and other parameters from the unit's `EnvironmentFile=` (the same file [[10-session-lifecycle-orchestration-plan#Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring]] already populates), calls Step 2.1's pure argv-construction function with those values, and execs `jailer` with the resulting argv (which itself execs `firecracker`). Add `Delegate=yes` and `IPAddressDeny=any` as unit directives on `agentvm-session-vm@.service`, alongside its existing directives (`RuntimeMaxSec=`, `Requires=`/`After=` on the two singletons, `ExecStartPre=`/`ExecStopPost=` for slot management, `Restart=no`) — do not remove or restructure any of those.

Verify: reusing [[10-session-lifecycle-orchestration-plan#Step 2.6 — Full unit-graph atomic-launch and stop-cascade proof]]'s test harness pattern, start a real session's target and confirm the VM unit now execs a real `jailer`/`firecracker` pair (not the sleep placeholder) chrooted under a session-specific uid/gid matching the slot index recorded in its `EnvironmentFile=`. As the `needs_kvm`+`needs_root` cgroup-delegation integration test named in [[14-testing-strategy#Cgroup delegation]], confirm `Delegate=yes` and jailer's own `--cgroup-version 2` nested cgroup coexist without one clobbering the other's limits — inspect the resulting cgroup tree and confirm systemd's delegated subtree and jailer's nested cgroup both exist without error. Confirm `IPAddressDeny=any` is in effect (the jailed process cannot open an IP socket of any kind, even though it wouldn't try to). This closes Chunk 2: a real, hardened jailer invocation now runs where a placeholder sleep script ran before.
```

## Step 3.1 — `min_timer_period_us` and `nosmt` host kernel tuning

Chunk 3, first step. Host-wide, independent of any single session; independent of Chunk 1/2's session-shaped work.

```text
Context already built: nothing from this chunk yet — this is host-wide kernel/module configuration, independent of the per-session hugepage and jailer work in Chunks 1–2.

Specification facts to ground this task in: `min_timer_period_us` lowers host CPU overhead from guest-injected timer interrupts (via the `kvm-pit` kernel thread, addressed in the next step). It is applied via a KVM kernel module parameter, made explicit in host config (`boot.extraModprobeConfig` or equivalent, `options kvm min_timer_period_us=<N>`) rather than an ad hoc one-off `modprobe` call — the exact value needs measuring against this guest kernel's actual timer usage, not assumed; pick a documented, clearly-labeled starting value and note in-config that it may need tuning once real timer-interrupt-rate data exists. Separately, SMT is disabled (`nosmt` on the host kernel cmdline), per Firecracker's own guidance that SMT is frequently a precondition for cross-tenant speculation-based information leaks — this project's concurrent agent sessions are exactly the "tenants sharing a physical host" scenario that guidance warns about. This is designed for the eventual bare-metal deployment target; the current Hyper-V-nested dev environment can't actually enforce this at the physical layer, which is expected and acceptable for dev — document this limitation in-config rather than silently expecting it to take effect in dev.

Task: add `options kvm min_timer_period_us=<N>` (a documented placeholder value, clearly labeled as needing real measurement) to the host's `boot.extraModprobeConfig`, alongside the `nx_huge_pages=never` entry from Step 1.2 in the same mechanism. Add `nosmt` to the host kernel's boot command line. Add a comment at the `nosmt` setting noting explicitly that the current nested-virtualization dev environment cannot enforce this at the physical layer, and that the setting is real and effective on the eventual bare-metal target.

Verify: boot the host and confirm `/sys/module/kvm/parameters/min_timer_period_us` reports the configured value, and confirm `/proc/cmdline` contains `nosmt`. In the current nested-virt dev environment, additionally confirm (and record as an expected, documented limitation, not a failure) whether SMT siblings are actually visible in `/sys/devices/system/cpu/cpu*/topology/thread_siblings_list` despite `nosmt` — this is expected to still show siblings in this dev environment per the specification's own caveat, and the check's job is to confirm that expectation, not to treat it as a bug.
```

## Step 3.2 — `kvm-pit` cgroup placement `ExecStartPost=` script

Chunk 3, second and final step. Adds a second `ExecStartPost=` directive to `agentvm-session-vm@.service`, alongside the slot-release one [[10-session-lifecycle-orchestration-plan#Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring]] already added (systemd runs repeated `ExecStartPost=` directives in order; this does not replace that one). Builds on Step 2.2's real jailer/firecracker `ExecStart=` — there is no real firecracker process to find a `kvm-pit` thread under until that exists.

```text
Context already built: `agentvm-session-vm@.service` with a real jailer/firecracker `ExecStart=` (Step 2.2), `Delegate=yes`, `IPAddressDeny=any`, and an existing `ExecStartPost=` that releases this session's concurrency slot (from [[10-session-lifecycle-orchestration-plan#Step 2.4 — `recv-proxy` real unit and slot acquire/release wiring]]) — this task adds a second, independent `ExecStartPost=` directive to the same unit, run in addition to that one, not in place of it.

Specification facts to ground this task in: the `kvm-pit` kernel thread (created via `kthread_run_worker(0, "kvm-pit/%d", pid_nr)` in `arch/x86/kvm/i8254.c`, per the spec's own verification against kernel source) is actually forked from the global `kthreadd` (PID 2) context, not from firecracker's own process tree — the `%d` in its name is cosmetic, not a real parent/cgroup relationship. `Delegate=yes` cannot reach it, since delegation only covers processes forked from the unit's own tree. The mitigation: an `ExecStartPost=` script on the VM unit locates the `kvm-pit/<tid>` task (scanning for a TID under firecracker's own `/proc/<pid>/task/`) and writes its PID into the unit's own `cgroup.procs`, pulling it into the delegated cgroup by hand.

Two risks are flagged by the spec as unconfirmed, #open-question, not to be assumed away: (1) PIT creation is lazy — it happens on first guest PIT access, not at process start — so a single-shot poststart check may race it and needs a retry/poll loop rather than one check-and-done; (2) whether a kernel-thread PID can be freely migrated via `cgroup.procs` the way a normal process's can has no definitive kernel documentation either way, per the spec's own search. This task's job includes surfacing both risks as concrete, observed test outcomes — not resolving them by assumption.

Task: build the `ExecStartPost=` script: given the VM unit's own firecracker PID (from the unit's own `MAINPID` or an equivalent lookup), poll `/proc/<firecracker-pid>/task/` for a task whose `/proc/<tid>/comm` matches `kvm-pit`, with a bounded retry/poll loop (not a single-shot check) to account for lazy PIT creation. On finding it, write that TID into `/sys/fs/cgroup/<this-unit's-delegated-path>/cgroup.procs`. Log clearly, distinguishably, whether: the thread was found within the poll window, the write to `cgroup.procs` succeeded, or either step failed — three distinct outcomes, not one generic pass/fail.
```
