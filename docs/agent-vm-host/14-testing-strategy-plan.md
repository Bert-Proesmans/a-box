# Testing Strategy — Implementation Plan

## Blueprint

[[14-testing-strategy]] is unlike every other spec in this collection: it names a repo-wide test-marker convention (`needs_kvm`/`needs_root`/`needs_bpf`, unmarked-runs-anywhere by default) and then enumerates concrete test scenarios — but almost every scenario it enumerates is a *verification step another component's plan already had to build for its own reasons*, per this backfill effort's own instruction to those agents to build their named scenario inline rather than wait for this plan. Checking each of this spec's named scenarios against the plans that exist:

**Unit tests, no VM needed:**
- "Receiver read-loop cap logic" (fake socket) — built at [[07-bpf-monitoring-plan#Step 4.1 — Standalone, growth-bounded receiver]], *before* this backfill effort even started ("proved standalone against synthetic bytes"). Covered, not rebuilt.
- "Idle-watchdog mtime-comparison logic" (fake clock, fake files) — built at [[11-session-transcript-receivers-plan#Step 4.1 — Idle-watchdog mtime-comparison logic]], which states outright it is "exactly the needs_kvm-free unit-test scenario 14-testing-strategy names for the idle watchdog." Covered.
- "Unit-file/target rendering" (rendering the session unit graph against fixture session IDs) — **not built, and not buildable as originally conceived.** [[10-session-lifecycle-orchestration-plan#Step 2.1 — Session directory/metadata conventions and the target + VM-unit skeleton]] made an explicit plan-level architecture decision to install the per-session unit set as static systemd *template* units (`agentvm-session@.target`, `agentvm-session-vm@.service`, etc., using systemd's own `%i` instance substitution) "rather than rendering full unit file text per launch." There is no `render_*` function left to fixture-test — the spec's illustrative naming implied one, but the chosen design doesn't have one. The closest existing proof is 10's own Step 2.1 Verify (a hand-written fixture session id + `params.env`, `systemctl start agentvm-session@<test-id>.target`), which needs a working systemd but not `/dev/kvm` at that point in the graph (the VM unit's `ExecStart=` is still a placeholder there). This plan does not invent a new unit test for a function that doesn't exist; flagged as an open gap below rather than guessed at.
- "Jailer invocation argv" (pure function, mirroring `build_cap_drop_plan`) — built at [[12-production-hardening-plan#Step 2.1 — Jailer invocation argv (pure function, unit-tested)]], explicitly citing this same spec note by name. Covered. (`build_cap_drop_plan` itself lives in [[04-guest-pid1-init-plan]], already built before this backfill; [[08-in-guest-hardening-plan]] does not build a version of this test — it only independently verifies the capability drop's *runtime effect*, not its argv-construction, at its own Steps 1.1–1.2.)

**`needs_kvm` integration tests:**
- "Hugepage boot-time benchmark" — built at [[12-production-hardening-plan#Step 1.3 — Firecracker machine-config `huge_pages` wiring]], citing this spec note by name. Covered.
- "Growth-bounding" (a receiver fed past 100 MB caps at exactly that size) — built twice, once per capped stream: [[11-session-transcript-receivers-plan#Step 1.1 — `recv-bpf`: real receiver wiring & cap-cascade proof]] for `bpf.jsonl`, [[11-session-transcript-receivers-plan#Step 2.3 — Real-graph wiring, attach-state independence, and cap-cascade proof]] for `terminal.jsonl`. Covered.
- "Idle watchdog" (idle session stopped at 10 minutes, active one isn't) — built at [[11-session-transcript-receivers-plan#Step 4.2 — Idle-watchdog real wiring & stop-cascade trigger]], citing this spec note by name. Covered.
- "Launch-atomicity" (inject a failure in a required unit, e.g. an already-bound vsock path; confirm the whole target fails with no leftover units) — built **twice**: generically at [[10-session-lifecycle-orchestration-plan#Step 2.6 — Full unit-graph atomic-launch and stop-cascade proof]] (induces a placeholder helper's non-zero exit) and again, for real, at [[13-error-handling-failure-modes-plan#Step 1.1 — Real-graph launch-atomicity proof and failure-surfacing verification]] (the exact named already-bound-vsock-path scenario, against the fully-real graph). 13's plan text frames this deliberately as "prove the same behavior against the real graph, not a placeholder" rather than blind duplication — but from a scenario-ownership standpoint both plans claim "Launch-atomicity" as their own verification step. Flagged below for the coordinator, not resolved here.

**`needs_kvm`+`needs_root` integration tests:**
- "`kvm-pit` placement" — built at [[12-production-hardening-plan#Step 3.2 — `kvm-pit` cgroup placement `ExecStartPost=` script]], citing this spec note by name (`#open-question` risks included). Covered.
- "Cgroup delegation" — built at [[12-production-hardening-plan#Step 2.2 — Wire jailer argv into the VM unit: `Delegate=yes`, `--cgroup-version 2`, `IPAddressDeny=any`]], citing this spec note by name. Covered.

That accounts for every scenario this spec names. What is left, and what this plan actually builds, is the one thing every one of those citing plans explicitly declined to build for itself: the shared marker mechanism. [[13-error-handling-failure-modes-plan#Step 1.1 — Real-graph launch-atomicity proof and failure-surfacing verification]] states this most plainly — it marks its own test `needs_kvm` "in a plain comment/docstring per this repo's naming convention without building the marker mechanism itself," and [[10-session-lifecycle-orchestration-plan]]'s Related section calls this note "that note's own future plan." [[10-session-lifecycle-orchestration-plan#Step 1.1 — Config file schema, loader, and defaults]] confirms this subsystem's host-side orchestration language is Python, so this plan's tooling is pytest — the `@pytest.mark.needs_kvm`-style decorator every citing plan's test already writes as a bare comment is real code nowhere yet. This plan builds that: pytest marker registration, a live environment-detection skip condition per marker (not a hardcoded stub), and a documented CI-safe-vs-full-hardware invocation split matching "unmarked tests run anywhere, including CI without virtualization."

**Open gap check.** Re-reading [[15-decisions-log]] fresh: its "Still open" section contains exactly one entry, "Resource limits → systemd unit property mapping" (relates to [[12-production-hardening]]) — not relevant to this spec's content. This plan flags two gaps of its own instead, neither guessed at nor silently patched into another plan: (1) the "Unit-file/target rendering" scenario as the spec describes it has no corresponding artifact to test, since [[10-session-lifecycle-orchestration-plan]] chose static template units over per-launch rendering — a spec-vs-chosen-design mismatch for the coordinator to note, not this plan's to resolve by inventing a render function nobody else built. (2) "Launch-atomicity" is verified by both [[10-session-lifecycle-orchestration-plan#Step 2.6 — Full unit-graph atomic-launch and stop-cascade proof]] and [[13-error-handling-failure-modes-plan#Step 1.1 — Real-graph launch-atomicity proof and failure-surfacing verification]] — not a defect (13's version is deliberately against the real, not placeholder, graph), but a genuine duplicate scenario claim worth the coordinator's awareness.

## Step 1.1 — Marker registration and environment-detection skip fixtures

Chunk 1, first step. Foundation for this plan — nothing precedes it. This is the mechanism every citing plan ([[10-session-lifecycle-orchestration-plan]], [[11-session-transcript-receivers-plan]], [[12-production-hardening-plan]], [[13-error-handling-failure-modes-plan]]) marks its own `needs_kvm`/`needs_root`/`needs_bpf` tests against as a bare comment, deferring the real enforcement to here.

```text
You are building the one piece of shared test infrastructure this Firecracker-based guest VM subsystem's test suite has been referencing by name, in plain comments and docstrings, without anyone yet building it: the needs_kvm/needs_root/needs_bpf pytest marker mechanism.

Specification facts to ground this task in: this is a repo-wide convention. needs_kvm marks a test requiring /dev/kvm. needs_root marks a test requiring elevated privileges (loop-mounts, BPF load, cgroup/jailer operations). needs_bpf marks a test requiring BPF load capability. Unmarked tests must run anywhere, including CI without virtualization — that property must hold by construction (no marker means no skip condition is ever applied), not by every test author remembering to leave a test alone. Per this project's own resolved eBPF-load-privilege decision, tracepoint/kprobe BPF program types need CAP_BPF plus CAP_PERFMON specifically (plain CAP_BPF alone is not sufficient), and this project did not judge a fine-grained capability grant worth chasing for a process that drops every capability moments after loading anyway — so a needs_bpf check in this test suite should test for genuine BPF-load-capable privilege (in practice, root-equivalent), not attempt to probe for the exact CAP_BPF/CAP_PERFMON pair via a more surgical mechanism no other part of this project uses either. This subsystem's host-side orchestration code is Python, so its test suite is pytest.

Task: build a shared conftest.py (placed at this test suite's shared root, alongside wherever this project's existing and future test modules already live) that: (a) registers needs_kvm, needs_root, and needs_bpf as known pytest markers (so using them produces no "unknown marker" warning); (b) implements a live environment-detection check for each — needs_kvm: /dev/kvm exists and is both readable and writable by the current process; needs_root: the current process's effective UID is 0; needs_bpf: BPF-load-capable privilege, treated in this implementation as equivalent to the same root check needs_root uses, per the grounding above — do not invent a separate, more granular capability probe; (c) implements a pytest_collection_modifyitems hook that, for every collected test item carrying one or more of these three markers, adds a skip marker with a distinct, human-readable reason (naming which condition failed, e.g. "requires /dev/kvm, not present or not accessible") whenever the corresponding environment check fails for this run, and leaves the item alone (no skip added) whenever the check passes. A test item carrying none of the three markers must never be touched by this hook, under any environment condition — this is what makes "unmarked runs anywhere" the suite's actual default rather than a documented intention.

Task, continued: write a small throwaway test module living alongside conftest.py containing exactly four test functions: one marked needs_kvm, one needs_root, one needs_bpf, one carrying no marker at all — each body trivially passes (e.g. assert True) so the only thing under test is whether each one runs or is skipped, not its own logic.

Verify: run this test module with each of the three environment checks monkeypatched to report "unavailable" (simulating an unprivileged, non-KVM, non-BPF-capable environment, e.g. a bare CI container) and confirm: the three marked tests are each reported skipped with a distinct, correct reason identifying which condition failed, and the unmarked test runs and passes. Then run again with each check monkeypatched to report "available" (simulating this project's actual target host) and confirm all four tests now run and pass, with no skip applied to any of them. This closes the loop: the marker convention this project's other plans have so far only referenced as a placeholder comment now has real, working enforcement behind it, self-verified against both ends of the availability spectrum before any other plan's real needs_kvm/needs_root/needs_bpf test ever depends on it.
```

## Step 1.2 — CI-safe vs full-hardware invocation profiles

Chunk 1, second and final step, closing the plan. Builds directly on Step 1.1's registered markers and skip hook — this step turns "unmarked tests run anywhere, including CI without virtualization" from a per-test skip behavior into an actual, documented, two-profile way of invoking the suite.

```text
Context already built: a shared conftest.py (Step 1.1) registering needs_kvm/needs_root/needs_bpf as pytest markers, with a collection hook that skips a marked test (with a distinct reason) whenever its corresponding environment check fails, and leaves unmarked tests untouched regardless of environment. A throwaway four-test module (one per marker, one unmarked) already proves this skip behavior works in both an under-provisioned and a fully-provisioned environment.

Specification facts to ground this task: unmarked tests must run anywhere, "including CI without virtualization" — this implies CI is expected to actually invoke the suite in a mode that never even attempts the hardware-dependent tests, not merely rely on Step 1.1's per-test skip-with-reason path to quietly no-op them one at a time on every CI run. This project's actual target host, by contrast, has /dev/kvm, root, and BPF-load capability all available, and is where the needs_kvm/needs_root/needs_bpf tests are meant to actually execute, not merely be exercised for their skip logic.

Task: define two named, documented pytest invocation profiles for this suite: a "ci"/portable profile that runs pytest -m "not needs_kvm and not needs_root and not needs_bpf" (excluding all three marker categories via pytest's own -m selection, a mechanism distinct from Step 1.1's per-test skip-with-reason path — exclusion here means the marked tests are never even attempted, not attempted-then-skipped), and a "full" profile that runs the suite with no -m filter at all, intended for this repo's actual target host. Record both invocations in whatever form matches this repo's existing convention for such documented commands (e.g. a pytest.ini/pyproject.toml markers section plus two named entries, or a thin wrapper script/Makefile target) so a future contributor finds the two profiles in one place rather than having to reconstruct the -m expression from this spec's prose. State explicitly, next to the two profiles, that a test carrying no marker must always pass under the "ci" profile — that is the concrete contract "unmarked tests run anywhere" makes, and a future unmarked test that only works with hardware or elevated privilege present has violated it, not the profile.

Verify: run the "ci" profile against Step 1.1's four-test module in an unprivileged, non-KVM environment and confirm exactly the unmarked test executes, with the three marked tests excluded from the run entirely (not reported as individually skipped-with-reason — confirm the profile's own summary output reflects exclusion, distinct from Step 1.1's skip-with-reason mechanism). Run the "full" profile against the same module in the same under-provisioned environment and confirm it reproduces Step 1.1's original skip-with-reason outcome for the three marked tests, with the unmarked test still passing. This closes the plan: the repo-wide needs_kvm/needs_root/needs_bpf convention this spec names now has both real enforcement (Step 1.1) and a working, documented two-profile invocation contract (this step) for CI versus real-hardware runs — the one piece of infrastructure every other already-planned component's tests have so far only referenced by name.
```
